# 551 低速机制诊断 v2

v1 的真实 GPU 结果已证明：恢复 CAN 分支只把首段参考从 4.1156 提高到 4.1359 m/s；输入速度4→16的整条规划最大差异约1 mm。不能把配置错配当作主要低速根因。

本版本保持所有生产源文件、模型权重、冻结 A/B 不变，不启动车辆驾驶。先复用已有数据进行 CPU 审计，再用一个驻留模型执行16次离线推理，保存内部特征及数值干预。未获得 v2 GPU 输出前不宣布已找到主要根因。

CPU 已核查：训练/运行 model 配置只有已知的 CAN 开关差异；实际模型投影矩阵按原编码器采样时，前方0～40 m、左右各4 m走廊约97.2%的柱采样被至少一个相机覆盖，排除“前方几乎完全投影不到图像”。这不认证图像特征质量。A-v4 的实际速度中位数约3.74 m/s，而模型 SDC 包围盒速度中位数约1.98 m/s，存在明显低估；包围盒速度本身并非规划头的显式速度参数，不能把这个相关现象直接当因果证据。

## 预定对照

7次独立首帧条件：原渲染基线、原始真实RGB、真实RGB恢复CAN、真实RGB再恢复预训练相机embedding、均匀图像负对照、右转导航命令、仅覆盖SDC包围盒速度。每次完整清空历史和跟踪缓存并设置同一种子；基线必须在1e-4 m内复现已保存 A 首帧规划。

另3组各3帧的真实记录历史：0.1 s采样history-BEV（源帧18/19/20）、0.5 s采样history-BEV（10/15/20）、0.5 s采样current-BEV（10/15/20）。组内保留完整历史，不重置；各组最后都在相同源第20帧、相同绝对位姿、相同真实图像和当前记录速度下比较。不同采样组的历史内容不同，结果只能归因于相应采样/历史策略，不伪装成同一历史下单独修改时间戳。

真实RGB严格复用551实际相机0/2/1对应front/right/left，按原框架先半尺寸双线性缩放再去畸变。未来帧图像、位姿只用于本次**离线记录回放**，不进入在线驾驶选择。没有相应真实深度时明确移除旧渲染深度，不能把源第10帧深度当作其他帧测量。原始神经规划不使用这些后处理深度。源速度用相邻记录位姿作离线中央差分，不能把此数据准备过程宣称为在线当前状态估计。

## 模型内部数值核验

原始 forward 返回值保持不变，记录规划融合后的自车/导航查询、实际BEV+位置特征及其范数/方差。重建的查询必须与原注意力输入一致，重放原注意力输出经原回归头/cumsum后的轨迹必须与最终导出规划一致，否则停止分析。

两种额外规划头干预只输出诊断参考：在保持视觉memory时清零融合输入中的自车轨迹/跟踪特征、保留导航特征；在保持自车查询时把BEV输入清零，保留原位置编码并经过原adapter。它们用于区分直接BEV路径与SDC查询路径的贡献，不是可采纳的驾驶补丁，也不能把分布外消融单独作为场景泛化证书。

CPU 测试检查钩子前后原始返回值逐元素相同、权重不变、规划头重放一致、历史组内不清空状态，以及时序组最终观测严格对齐。合成小网络测试不冒充 UniAD GPU 效果。

## 执行

默认产物 `phase26/uniad_speed_mechanism_v2`。已准备的输入和代码内容哈希固化，现有有效结果直接复用；已确认退出的失败启动会移入 `failed_attempts/` 保留，并重新从第1个条件开始；历史对照不从中途拼接。运行中的任务、存活状态不明的部分任务和已有结果均不覆盖。发布目录的诊断 hooks 按绝对文件路径加载，避免与 UniAD 内部 hooks 同名冲突。

```bash
D=${HUGSIM_ROOT}/integrations/uniad-speed-mechanism-v2
bash "$D/run.sh" prepare
bash "$D/run.sh" probe
```

入口检查CUDA、GPU服务锁、实际空闲状态及STOP，不停止其他窗口的工作。只加载一次模型，不渲染新场景、不运行MPC、不改写 A/B。完成后 `result.json` 汇总16次规划与特征消融，`worker/step_*/mechanism_audit.json` 记录实际历史/开关，`planner_features.json` 和 `planner_ablations.npz` 保存分段证据；基线和真实RGB首帧还保留 `planner_inputs.npz`，便于后续 CPU 复核，避免重复启动模型。

`bash "$D/run.sh" inspect` 仅重读并核验已完成实验。结果必须先定位是哪一段出现异常，再决定新 A 的修复；B保持等待。
