# UniAD 低速诊断

只读已有 A-v1/v2/v4、模型源代码和实际权重。独立诊断不修改旧 A/B、冻结配置、UniAD 源代码或权重，不启动新驾驶任务。

已确认：实际权重元数据 `meta.config` 中 `use_can_bus=True`，而当前初始化加载的 `base_e2e.py` 为 `False`。`load_checkpoint` 只加载张量，不会把训练时的布尔配置自动覆盖到当前模型。模型虽收到 `can_bus[13]` 中的车速，但相应 MLP 特征乘以 False；规划头没有单独的实际车速参数，依赖 BEV 和模型推断的 SDC 查询。

CPU 核验直接执行原 `get_bev_features` 方法，加载该权重中的 CAN MLP，编码器替换为查询捕获器以隔离注入点。速度 4→16 m/s，在关闭分支时注入查询逐元素完全相同（差异 0）；开启时最大绝对差异约 0.08798。这证明输入分支问题，不是完整 GPU 规划效果验证。

A-v4 的 188 步外部参考全部保留原始纵向节点，道路门禁没有覆盖动作；车辆硬上限为 30 m/s。旧 A 的实际初速 16 m/s 时首参考只有 4.12856 m/s，模型参考已低速；控制器据此制动。原场景源第10帧真实记录速度约20.0966 m/s。4 m/s 是后续为适应已有参考采用的初始化，不能把这一实验当正常速度基准。

尚未证明恢复一个开关就能解决全部低速。当前状态输入另有未填加速度、将转向速率当角速度、四元数仅含航向等问题；三相机域迁移、current-BEV 策略和输入时序贡献也没有被这项 CPU 实验排除。0.1 s 观测间隔与0.5 s 规划节点间隔不同，但这不是把全部轨迹乘5的依据。

## 最小 GPU 证据

`probe` 使用同一张已保存的实际 A 首帧相机图像、相同位姿和相同其他输入，只加载一次原冻结 UniAD，运行四个独立冷启动条件：CAN 分支关闭/开启 × 声明车速4/16 m/s。每次使用现有完整 episode reset 清理 BEV、跟踪、元数据、参考姿态和参与者缓存，重设相同种子，检查实际 CAN bus 与实际开关。

这是**单帧离线输入反事实实验**，不是实际执行的新速度，也不是闭环驾驶结果。关闭分支/4 m/s 必须在预定1e-4 m容差内复现已保存 A 首帧规划；关闭分支的速度变化必须在1e-5 m内不影响规划，否则比较无效。输出分别报告恢复开关、变化速度所造成的原始规划差异，不预设一定加速，也不把非零差异解释为正常驾驶恢复。

```bash
D=${HUGSIM_ROOT}/integrations/uniad-speed-audit
bash "$D/run.sh" audit      # 已完成，可复核 CPU 证据
bash "$D/run.sh" prepare    # 已完成，复用冻结输入
bash "$D/run.sh" probe      # 在空闲 GPU 节点执行，约一次模型启动+4次推理
```

默认输出 `phase26/uniad_speed_audit_v1`：`report.json` 是现有证据，`checkpoint_training_config.py` 是从实际权重导出的原配置；GPU 完成后才生成 `gpu/result.json`。GPU 入口检查 CUDA、服务锁、实际空闲和 STOP，不终止其他任务，不覆盖部分或失败任务。

后续顺序：先完成配置/状态输入对照，依据证据修复状态契约，冻结一个正常速度的新 A 并验证道路与制动能力；通过后再按同样条件建立 B。不会在本次诊断中直接开启旧配置、强行拉长轨迹或重跑完整 B。
